
# Learn Harness Engineering — AI 编程智能体脚手架工程

> 来源：Walking Labs，https://walkinglabs.github.io/learn-harness-engineering/zh/
> 摘录时间：2026-05-25

## 概述

一门专注于 AI 编程智能体工程化落地的课程。参考资料包括 OpenAI、Anthropic 的 harness engineering 文章和 Awesome Harness Engineering 项目。

核心论点：**模型能力强 ≠ 执行可靠。问题不在模型，在 harness（马具/脚手架）。**

引用实验：
- **Anthropic**：同一个 prompt 和模型，裸跑 $9/20min 游戏跑不起来，配上 harness 后 $200/6h 能玩
- **OpenAI**：3 个工程师 5 个月用 Codex 写出 100 万行代码（1500 个 PR），关键是搭好了 harness

## 课程结构

- **讲义**（12 讲）— 从理论到实践
- **项目**（6 个渐进式实战）
- **资料库** — 可复用的模板文件
- **Skills（技能集）** — 自包含的 prompt 模板（harness-creator 技能）

## 12 讲讲义速览

### L01 | 模型能力强，不等于执行可靠
- SWE-bench 50-60% 通过率 ≠ 真实任务表现
- 五种失败模式：需求模糊、隐性约定、环境缺口、验证缺失、跨会话状态丢失
- 核心原则：**遇到失败，先修 harness，别先换模型**

### L02 | Harness 到底是什么
- Harness = 模型权重之外的一切工程基础设施
- **Harness 五子系统模型**（全课核心框架）：
  1. **指令子系统** — AGENTS.md/CLAUDE.md，告诉 agent 项目怎么用
  2. **工具子系统** — 保证 agent 有足够的 shell/API 权限
  3. **环境子系统** — 仓库即唯一事实来源，依赖/配置齐全
  4. **状态子系统** — 跨会话持久化，防止"上下文焦虑"
  5. **反馈子系统** — 测试/lint/类型检查等可验证的完成定义

### L03 | 让代码仓库成为唯一的事实来源
- 不在仓库里的知识对 agent 来说 = 不存在
- **知识可见性缺口**：隐性知识中未写入仓库的比例
- **全新会话测试**：开全新 agent 会话能否回答五个基本问题
- **ACID 类比**：把数据库事务管理原则用到 agent 状态管理
- 知识靠近代码、最小但完备、和代码一起更新

### L04 | 把指令拆分到不同文件里
- 巨型指令文件陷阱：膨胀→中间迷失→优先级冲突→维护衰减
- **入口文件** 50-200 行，只放概览、硬约束和链接
- **按需展开**：专题文档放 docs/，agent 需要时才去读
- 利用"Lost in the Middle"效应，重要信息放顶部或底部
- 实战案例：拆分后成功率从 45%→72%，安全约束遵循率 60%→95%

### L05 | 让跨会话的任务保持上下文连续
- 上下文窗口有限，长任务一定会跨会话
- **上下文焦虑**：agent 在接近上下文限制时匆忙收尾
- 三个工具：PROGRESS.md（进度文件）+ DECISIONS.md（决策日志）+ git 检查点
- **重建成本**是关键指标：好的 harness 让新会话 3 分钟恢复到可执行状态
- 对比数据：重建时间减少 78%，功能完成率 58%→100%

### L06 | 让 agent 每次工作前先初始化
- 初始化和实现的优化目标不同，混在一起两头都做不好
- 初始化产出：可运行的环境 + 可验证的测试框架 + 启动就绪清单 + 任务分解
- **启动就绪清单**：能启动、能测试、能看进度、能接手下一步
- **热启动** > 冷启动：用项目模板预置标准化基础设施
- Anthropic 数据：独立初始化提升多会话功能完成率 31%

### L07 | 给 agent 划清每次任务的边界
- **WIP=1**：任何时刻只允许一个任务在"进行中"
- **过度延伸（Overreach）** 和 **不足完成（Under-finish）** 是共生的
- **完成证据**必须是可执行的验证命令，不是"代码看起来没问题"
- 数据：WIP=1 使完成率 87.5% vs 37.5%，代码行数和完成率弱负相关

### L08 | 用功能清单约束 agent 该做什么
- 功能清单是 **harness 原语**：调度器、验证器、交接器都依赖它
- **三元组结构**：(行为描述, 验证命令, 当前状态)
- 状态机：not_started → active → blocked → passing（由 harness 控制转移）
- 通过状态门控：passing 的唯一方式是验证命令执行成功
- 结构化清单比非结构化笔记完成率高 45%

### L09 | 防止 agent 提前宣告完成
- **置信度校准偏差**：神经网络系统性过度自信（Guo et al., 2017）
- **终止标准必须外部化**，不信任 agent 的"感觉"
- **三层终止校验**：语法 → 行为 → 系统，层层递进
- **错误消息要包含修复指导**，形成自我修正闭环
- Anthropic 三 agent 实验：裸跑 $9 失败 vs 带 evaluator $200 成功

### L10 | 跑通完整流程才算真正验证
- **组件边界缺陷**：单元测试系统性盲视（隔离设计恰好无法检测交互问题）
- 端到端测试不仅检测缺陷，还**改变 agent 的编码行为**
- 架构规则必须可执行：不写在文档里等人来看，而是每次提交自动检查
- **审查反馈提升**：每次发现重复问题就加一条自动化规则

### L11 | 让 agent 的运行过程可观测
- **双层可观测性**：运行时信号（发生了什么）+ 过程工件（为什么）
- **冲刺合同（Sprint Contract）**：任务开始前协商范围、验证标准、排除项
- **评估评分标准**：把"好不好"变成可量化的评分
- 可观测性缺失 → 30-50% 会话时间浪费在重复诊断
- Anthropic DAW 实验：三 agent + 完整可观测性 $124.70/3h50m 完成

### L12 | 每次会话结束前都做好交接
- 清洁状态五维度：构建通过 + 测试通过 + 进度已记录 + 无过时工件 + 启动路径可用
- **即时清理**（每次会话结束时）+ **定期清理**（每周一次）
- **质量文档**：对每个模块持续评分，跟踪代码库健康度
- **定期简化 harness**：随模型能力提升移除不再必要的约束
- 12 周对比：有清洁策略 → 构建 97%/测试 95%/启动 9min vs 无策略 → 68%/61%/60min+

## 关键贡献

### 五子系统模型（在现有 wiki 基础上新增的框架）

这套模型比之前记录的 Anthropic/Cursor 对比更结构化：

1. **指令** — AGENTS.md/CLAUDE.md，着陆页式入口
2. **工具** — agent 可用的 shell/API/工具生态
3. **环境** — 仓库即规范，依赖/配置/验证命令齐全
4. **状态** — PROGRESS.md/DECISIONS.md/git 检查点
5. **反馈** — 三层终止校验 + 面向 agent 的错误消息

### 可操作的模板体系

课程附带的资料库给出了一系列可直接复用的文件：
- AGENTS.md 模板
- feature_list.json（JSON Schema）
- init.sh 启动脚本
- progress.md 进度日志
- session-handoff.md 交接模板
- evaluator-rubric.md 评审模板
- clean-state-checklist.md 收尾清单
