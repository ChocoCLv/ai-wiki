    10|# Learn Harness Engineering — AI 编程智能体脚手架工程
    11|
    12|> 来源：Walking Labs，https://walkinglabs.github.io/learn-harness-engineering/zh/
    13|> 摘录时间：2026-05-25
    14|
    15|## 概述
    16|
    17|一门专注于 AI 编程智能体工程化落地的课程。参考资料包括 OpenAI、Anthropic 的 harness engineering 文章和 Awesome Harness Engineering 项目。
    18|
    19|核心论点：**模型能力强 ≠ 执行可靠。问题不在模型，在 harness（马具/脚手架）。**
    20|
    21|引用实验：
    22|- **Anthropic**：同一个 prompt 和模型，裸跑 $9/20min 游戏跑不起来，配上 harness 后 $200/6h 能玩
    23|- **OpenAI**：3 个工程师 5 个月用 Codex 写出 100 万行代码（1500 个 PR），关键是搭好了 harness

    32|## 12 讲讲义速览
    33|
    34|### L01 | 模型能力强，不等于执行可靠
    35|- SWE-bench 50-60% 通过率 ≠ 真实任务表现
    36|- 五种失败模式：需求模糊、隐性约定、环境缺口、验证缺失、跨会话状态丢失
    37|- 核心原则：**遇到失败，先修 harness，别先换模型**
    38|
    39|### L02 | Harness 到底是什么
    40|- Harness = 模型权重之外的一切工程基础设施
    41|- **Harness 五子系统模型**（全课核心框架）：
    42|  1. **指令子系统** — AGENTS.md/CLAUDE.md，告诉 agent 项目怎么用
    43|  2. **工具子系统** — 保证 agent 有足够的 shell/API 权限
    44|  3. **环境子系统** — 仓库即唯一事实来源，依赖/配置齐全
    45|  4. **状态子系统** — 跨会话持久化，防止"上下文焦虑"
    46|  5. **反馈子系统** — 测试/lint/类型检查等可验证的完成定义
    47|
    48|### L03 | 让代码仓库成为唯一的事实来源
    49|- 不在仓库里的知识对 agent 来说 = 不存在
    50|- **知识可见性缺口**：隐性知识中未写入仓库的比例
    51|- **全新会话测试**：开全新 agent 会话能否回答五个基本问题
    52|- **ACID 类比**：把数据库事务管理原则用到 agent 状态管理
    53|- 知识靠近代码、最小但完备、和代码一起更新
    54|
    55|### L04 | 把指令拆分到不同文件里
    56|- 巨型指令文件陷阱：膨胀→中间迷失→优先级冲突→维护衰减
    57|- **入口文件** 50-200 行，只放概览、硬约束和链接
    58|- **按需展开**：专题文档放 docs/，agent 需要时才去读
    59|- 利用"Lost in the Middle"效应，重要信息放顶部或底部
    60|- 实战案例：拆分后成功率从 45%→72%，安全约束遵循率 60%→95%
    61|
    62|### L05 | 让跨会话的任务保持上下文连续
    63|- 上下文窗口有限，长任务一定会跨会话
    64|- **上下文焦虑**：agent 在接近上下文限制时匆忙收尾
    65|- 三个工具：PROGRESS.md（进度文件）+ DECISIONS.md（决策日志）+ git 检查点
    66|- **重建成本**是关键指标：好的 harness 让新会话 3 分钟恢复到可执行状态
    67|- 对比数据：重建时间减少 78%，功能完成率 58%→100%
    68|
    69|### L06 | 让 agent 每次工作前先初始化
    70|- 初始化和实现的优化目标不同，混在一起两头都做不好
    71|- 初始化产出：可运行的环境 + 可验证的测试框架 + 启动就绪清单 + 任务分解
    72|- **启动就绪清单**：能启动、能测试、能看进度、能接手下一步
    73|- **热启动** > 冷启动：用项目模板预置标准化基础设施
    74|- Anthropic 数据：独立初始化提升多会话功能完成率 31%
    75|
    76|### L07 | 给 agent 划清每次任务的边界
    77|- **WIP=1**：任何时刻只允许一个任务在"进行中"
    78|- **过度延伸（Overreach）** 和 **不足完成（Under-finish）** 是共生的
    79|- **完成证据**必须是可执行的验证命令，不是"代码看起来没问题"
    80|- 数据：WIP=1 使完成率 87.5% vs 37.5%，代码行数和完成率弱负相关
    81|
    82|### L08 | 用功能清单约束 agent 该做什么
    83|- 功能清单是 **harness 原语**：调度器、验证器、交接器都依赖它
    84|- **三元组结构**：(行为描述, 验证命令, 当前状态)
    85|- 状态机：not_started → active → blocked → passing（由 harness 控制转移）
    86|- 通过状态门控：passing 的唯一方式是验证命令执行成功
    87|- 结构化清单比非结构化笔记完成率高 45%
    88|
    89|### L09 | 防止 agent 提前宣告完成
    90|- **置信度校准偏差**：神经网络系统性过度自信（Guo et al., 2017）
    91|- **终止标准必须外部化**，不信任 agent 的"感觉"
    92|- **三层终止校验**：语法 → 行为 → 系统，层层递进
    93|- **错误消息要包含修复指导**，形成自我修正闭环
    94|- Anthropic 三 agent 实验：裸跑 $9 失败 vs 带 evaluator $200 成功
    95|
    96|### L10 | 跑通完整流程才算真正验证
    97|- **组件边界缺陷**：单元测试系统性盲视（隔离设计恰好无法检测交互问题）
    98|- 端到端测试不仅检测缺陷，还**改变 agent 的编码行为**
    99|- 架构规则必须可执行：不写在文档里等人来看，而是每次提交自动检查
   100|- **审查反馈提升**：每次发现重复问题就加一条自动化规则
   101|
   102|### L11 | 让 agent 的运行过程可观测
   103|- **双层可观测性**：运行时信号（发生了什么）+ 过程工件（为什么）
   104|- **冲刺合同（Sprint Contract）**：任务开始前协商范围、验证标准、排除项
   105|- **评估评分标准**：把"好不好"变成可量化的评分
   106|- 可观测性缺失 → 30-50% 会话时间浪费在重复诊断
   107|- Anthropic DAW 实验：三 agent + 完整可观测性 $124.70/3h50m 完成
   108|
   109|### L12 | 每次会话结束前都做好交接
   110|- 清洁状态五维度：构建通过 + 测试通过 + 进度已记录 + 无过时工件 + 启动路径可用
   111|- **即时清理**（每次会话结束时）+ **定期清理**（每周一次）
   112|- **质量文档**：对每个模块持续评分，跟踪代码库健康度
   113|- **定期简化 harness**：随模型能力提升移除不再必要的约束
   114|- 12 周对比：有清洁策略 → 构建 97%/测试 95%/启动 9min vs 无策略 → 68%/61%/60min+
   115|
   116|## 关键贡献
   117|
   118|### 五子系统模型（在现有 wiki 基础上新增的框架）
   119|
   120|这套模型比之前记录的 Anthropic/Cursor 对比更结构化：
   121|
   122|1. **指令** — AGENTS.md/CLAUDE.md，着陆页式入口
   123|2. **工具** — agent 可用的 shell/API/工具生态
   124|3. **环境** — 仓库即规范，依赖/配置/验证命令齐全
   125|4. **状态** — PROGRESS.md/DECISIONS.md/git 检查点
   126|5. **反馈** — 三层终止校验 + 面向 agent 的错误消息
